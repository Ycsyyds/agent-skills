# 专利组合挖掘与交底书撰写工作流

## 这个 skill 是干什么的

算法/系统工程师做了大量技术工作，但很少主动把工作成果整理成可申请的专利。本 skill 把"从一堆项目文档/代码/测试报告里挖出专利点，判断怎么组合成篇，查新，写成脱敏交底书，配图，复核"这套完整流程沉淀下来——这是从一次真实的多专利挖掘任务（LIVO SLAM 系统，最终产出 6 篇交底书）里提炼的方法论，不是纯理论模板。

**和已安装的 `patent-disclosure-skill` 的关系**：如果工作区里装了那个技能，直接复用它的两个工具——`tools/cnipa_epub_search.py`（国知局官方摘要查新，比通用网络搜索权威得多）和 `tools/mermaid_render.py` / `tools/md_to_docx.py`（图示渲染+导出 Word）。本 skill 补的是那个技能默认不强调的部分：**如何从零散的技术工作里系统性拉出候选点清单、如何判断该合并还是该拆、以及配图时用绘图类 MCP（如 draw.io）会踩的具体坑**。没装那个技能时，查新降级为通用网络搜索，配图降级为纯文字描述附图说明。

## 核心原则：先挖宽，再收窄

不要一上来就选一个点深挖成交底书。先按模块/机制把整个技术方向扫一遍，拉出尽可能多的候选点（哪怕后面被淘汰或合并），再决策。原因：候选点之间的关联（谁是谁的融合逻辑、谁和谁共享同一机制）只有在候选点齐全之后才看得出来，过早收窄会让最终专利组合支离破碎、内容重复披露、权利要求覆盖面窄。

## 工作流

### Step 1 · 挖掘候选点

来源优先级：项目内部技术分享文档/开发笔记（往往已经写清楚了"为什么这么做、和主流方案的区别"）> 架构文档/决策记录（含设计取舍）> 代码本身（成本最高，只在前两者缺失时兜底）。

对每个模块/机制，逐一判断是否可能构成候选点，并按下面的口径记录（**这一步全程不写具体实现细节**——不写阈值数值、变量/文件命名、代码结构，只写到"技术问题→方案概念→与现有技术的区别"这个抽象层级，原因见 Step 4 的脱敏红线）：

- **技术问题**：现有技术/主流开源方案（如果知道具体是哪个，点名，方便后续查新）在这一点上有什么缺陷
- **方案概念**：怎么解决的，用"模块""判据""状态""流程"这类通用词描述，不用代码里的实际命名
- **与现有技术的区别**：明确说出"主流方案 X 是怎么做的，本方案哪里不同"——这一句话就是新颖性论证的种子，没有这句话的候选点大概率经不起查新
- **初步风险分级**：低/中/高。判断依据见下面"怎么判断新颖性风险"

不要在这一步就否定看起来"太小"的点——很多小点在 Step 2 合并后会变成一个更完整专利里的从属权利要求，价值不小。

### Step 2 · 合并决策

拉完候选点清单后，逐对检查是否存在以下三种"应该合并"的信号，出现任一种就考虑合并：

1. **融合关系**：候选点 B 本质上是候选点 A、C 输出结果的融合/仲裁逻辑（比如"两个信号分别怎么算"是 A、C，"两个信号怎么安全地合成一个"是 B）——拆开披露会让 B 的存在理由讲不清楚，合并后是一条完整的感知-判断-融合逻辑链。
2. **同源材料**：多个候选点原本就来自同一份设计文档的不同章节（比如"怎么建"和"怎么维护回收"经常是同一份"XX 架构设计"文档里的两节）——按原文档的完整性合并，而不是按"挖掘时正好读到的顺序"分篇。
3. **重复披露**：两个候选点描述的实际上是同一个安全/校验机制，只是从不同角度各写了一遍（比如"运行时布局校验拒绝更新"在 A 篇里是"多态更新安全机制"的一部分，在 B 篇里又作为"某具体子系统的安全索引"的一部分出现）——合并去重，否则会被审查员质疑权利要求重叠。

同时注意**不该合并**的信号：问题域完全不同（比如"状态估计精度"和"数据管道完整性"），合并会破坏专利的单一性（同一发明构思要求），审查时容易被要求分案。宁可维持多篇，也不要为了"篇数好看"硬凑。

高风险点（见 Step 3）不要和低风险点合并到一篇——一旦被检索命中问题，会拖累整篇的其它内容，应保持独立，方便后续专利代理人单独处理。

### Step 3 · 查新

**每个候选点/合并后的专利都要查一遍，越早查越好**——挖掘阶段觉得"新颖"的点，查新之后可能发现是某篇几个月前刚发的论文/专利的核心机制，及时止损比写完交底书才发现好得多。

优先级：
1. 如果装了 `patent-disclosure-skill`：用它的 `tools/cnipa_epub_search.py`。**检索词要拆成语义块，一次工具调用只传一个词/短语**（该工具本身不做中文分词，长句子直接传进去很容易 0 命中——比如"滑窗多帧视觉里程计"整句传大概率 0 结果，拆成"滑动窗口""视觉里程计"分两次查，命中率高得多）。命中后重点看 `abstract` 字段，官方摘要比标题更能判断是否真的相关。
2. 没装该工具或它连不上（如国知局网站改版/WAF 拦截）：降级为通用网络搜索（arXiv + Google Patents 摘要），但要明确告知用户"这是初筛，不能替代 incoPat/CNIPA 专业检索，正式提交前必须补做"——不要让这句免责声明被用户当成套话跳过，通用网络搜索确实经常漏掉最相关的同领域中文专利（实测案例：通用搜索找到的都是国际论文，换成国知局官方检索后命中一篇结构上高度相似的国内专利申请，而这篇在通用搜索结果里完全没出现）。
3. 查到相关文献后，明确写出"哪一点像、哪一点不像"，而不是笼统写"存在类似技术"——审查阶段真正有用的是具体的区别点论证，不是"已排查"这句话本身。

### Step 4 · 撰写与脱敏

**标准交底书结构**（模板见 `assets/disclosure_template.md`，直接照抄框架填内容）：

```
发明名称 / 技术领域 / 背景技术 / 发明内容（要解决的技术问题 + 技术方案 + 有益效果）
/ 附图说明 / 具体实施方式 / 权利要求书（独立权利要求 + 从属权利要求）
/ 自审说明 / 检索与风险提示
```

权利要求写法：独立权利要求覆盖整个发明构思的核心（通常对应 Step2 合并后的"主线逻辑"），从属权利要求逐项收窄到具体子机制；如果合并了多个候选点，从属权利要求的顺序应该跟发明内容里"技术方案"分点描述的顺序一致，方便审查员和代理人对照阅读。

**脱敏红线（比"别泄露实现细节"更具体的清单）**：
- 不写具体阈值数值、参数配置（用"预设阈值""预设范围"代替实际数字）
- 不写变量名、文件路径、函数名、代码结构（用"状态分量""索引函数""观测模块"这类通用词）
- 不写客户/项目/场地名称——这一条经常被漏掉，因为大家第一反应只防"技术机密"，但项目材料里常有具体的客户项目名、楼盘/场地名、设备序列号，这些一旦进了专利就是公开文件，比技术细节泄露的问题更严重，必须逐条排查删除
- 补充实施例数据时（第三方测试报告等），把具体数字改成区间化表述（"降低约 10%"而不是"降低 10.3%"），把具体场景名改成"测试场景 A/B"，并在文档末尾单独加一段"数据来源说明（内部追溯，非交付正文）"注明原始出处和脱敏处理方式，方便内部审阅但明确标注**正式交付前要删除或移出正文**

**怎么判断新颖性风险（决定 Step2 是否要单独处理、Step3 要不要重点查）**：
- 风险低：具体的工程组合、边界条件处理、多个已知机制的特定连接方式（比如"用同一套算法同时求解正向反向映射保证互逆"——各部分都不新，但这个具体要求没人专门讨论过）
- 风险中：某个大方向本身有不少同期研究（比如"用特征值/条件数做退化检测"这类思路在 SLAM 领域已经是活跃方向），这时候不要单独就这一点申请，要靠"这个大方向下的具体组合细节"撑新颖性，写作时要把组合细节作为独立权利要求的必要限定，而不是笼统描述大方向
- 风险高：查新查到一篇公开时间早、技术方案高度重叠的论文或专利，且双方处理的是同一个核心技术问题——这种情况不要放弃，但要在背景技术段落里主动引用对比文献并论述结构性差异，把差异点写成独立权利要求的必要技术特征（不是写在说明书里就完事），并在检索与风险提示里明确标注"需专利代理人逐条权利要求比对"

### Step 5 · 配图

优先用 mermaid（`patent-disclosure-skill` 的 `tools/mermaid_render.py`）快速出草图——文本 DSL 好写、渲染快、失败率低。

如果需要更接近正式专利图纸的风格（纯黑白线条、矩形/菱形，没有 mermaid 默认主题的圆角彩色块），且有 draw.io 类 MCP（如 next-ai-draw-io）可用，重新画一遍。**这条路线有几个非明显的坑，踩过一次后总结如下**：

1. **决策菱形（rhombus）文字超过 6-8 个字就会溢出边框**——菱形的可用文字区域只有其外框尺寸的一半左右（居中的内接矩形），不是整个外框都能放字。长句子标签要么把菱形加宽到文字预期宽度的 2-3 倍，要么直接把标签缩短、把完整说明放回图注文字里（更符合专利图纸"图里只放精简标签，完整说明写在正文"的惯例）。
2. **正交边（orthogonalEdgeStyle）不显式指定 exitX/exitY/entryX/entryY 时，路由可能穿过图形本体**——尤其是当边的目标在源图形的"非直觉方向"时（比如从一个方框的顶边退出、但目标其实在下方），默认路由可能先穿过图形自身再绕出去，视觉上会看到线压在文字上。解决办法：给可能有歧义的边显式设置退出/进入的边和相对位置（如 `exitX=1;exitY=0.5` 表示从右边中点退出），选择在几何上朝向目标的那一侧退出，而不是让工具自动猜。
3. **导出 PNG/SVG 不支持并发调用**——同一个绘图会话只有一个共享的浏览器画布，同时发多个导出请求会互相干扰，某次的导出可能实际截到了另一次请求切换过去的页面内容（表现为文件保存成功但内容是错的，这不是猜测，是实测踩过的坑：并发导出后有一张图的文件名下存的其实是另一张图的内容，靠事后逐张查看才发现）。**必须一张一张顺序导出**，虽然慢，但能保证正确性；批量画完所有页面之后再统一顺序导出，不要边画边导出交替并发。
4. **导出前必须有一个真实打开、已加载该绘图会话 URL 的浏览器标签页**——纯数据操作（读取/新增页面）不需要，但截图导出需要一个"活的"页面来渲染。偶尔即使标签页开着，导出仍会随机超时，**重试 1-2 次基本都能成功，属于正常波动，不代表数据有问题**；但如果连续失败 3-4 次以上，就该停下来向用户确认标签页是否还开着/是否需要刷新，而不是无限重试下去。
5. **会话可能被重置（变回空白页），但内容不会真的丢**——如果 `list_pages` 突然显示只有 1 个空白页，说明绘图会话被重启了，不用惊慌重画：只要之前用 `export_diagram` 导出过一次完整的 `.drawio` 备份文件，用 `load_diagram` 重新加载该文件就能恢复全部页面，接着从上次中断的地方继续导出即可。**养成习惯：批量画完一批图后先导出一份全量 `.drawio` 备份，再逐张导出 PNG**，这样即使会话中途重置也不会真的从头再来。
6. 画完一批图后，**逐张实际查看渲染结果**（不要只看"导出成功"这个返回值就当作完成）——上述坑 1、2 都是导出"成功"但内容有缺陷，只有实际看一眼图片才能发现文字溢出、线压字，或者因并发冲突导致图文对不上的问题；尤其要重点复查刚经历过失败重试的那几页，这些页面最容易出现"返回成功但内容是别的图"的情况。
7. **不要偷懒只画"最核心的几张"就当作配图完成**——很容易先只画3张最重要的图省事，剩下的图留成纯文字描述，这个缺口在最终提交前的复核里非常显眼（数一下"附图说明"里列了几个"图N："，再数一下正文里实际有几个"### 图N"小节，两者必须一一对应）。宁可从一开始就规划清楚要画哪几张、就把它们全部画完，别指望"审查阶段再补"——真等到那个阶段，往返沟通、重新打开绘图会话、重新走一遍导出流程的成本比一开始就画完高得多。

### Step 6 · 复核

批量产出多篇后，做一轮统一复核，逐条对照。这一步经常不是一次性做完的——很可能在你以为"完成"之后，用户才想起还要补发明人信息、或者才决定真要提交而不只是内部草稿，把复核当成"提交前的一道常设关卡"而不是"写完就过一次"：

- [ ] 每篇的标题层级结构一致（技术领域/背景技术/发明内容→子项/附图说明→图N/具体实施方式/权利要求书/自审说明/检索与风险提示），方便代理人跨篇对照
- [ ] **附图说明列出的图数量 == 正文实际画出来的"### 图N"小节数量**，逐篇数一遍（这一条最容易漏，也最容易被审阅者一眼看出来）
- [ ] 附图与图注描述的内容真的对应（重新画图/重新导出后容易出现图文对不上或文件名指向错图的情况，务必人工看一眼，尤其是发生过导出失败重试的页面）
- [ ] **权利要求书末尾的装置权利要求和介质权利要求，引用的方法权利要求范围数字必须完全一致**（比如都是"权利要求1-5任一"）——这是从属权利要求增删后最容易忘记同步的地方，一条一条读太慢，直接搜"任一所述"这几个字，把每处引用的数字范围列出来比对最快
- [ ] 脱敏红线（Step4）逐条过一遍，特别是客户/项目/场地名称这条最容易漏
- [ ] **标记为"内部/非交付正文"的说明段落是否已经真正删除**——这类段落是为了内部追溯脱敏来源而写的，写的时候就该标注"正式交付前删除"，但标注不等于删除，复核时要真的执行这个动作，不要留给用户自己发现
- [ ] **发明人信息表头（姓名用真名不用花名、部门、联系方式、申请人/公司名、日期）是否已经补上**——这一项通常是用户在"准备提交"这个节点才会想起来问，主动确认一遍比等用户问更好
- [ ] 权利要求的限定语和说明书里强调的"与现有技术的区别点"一致——尤其是风险中/高的专利，独立权利要求必须包含那个区别点作为必要技术特征，不能只在说明书里提一句
- [ ] 每篇末尾的风险等级、优先级建议齐全，方便用户/专利代理人排优先级

**关于覆盖 docx 的一个操作细节**：重新生成 `.docx` 前，先看看同目录下有没有 `.~lock.<文件名>#`（LibreOffice）这类锁文件——有的话说明用户正开着这份文档在看，直接覆盖有冲突风险（用户之后如果保存，会把你刚生成的新版本盖掉）。遇到锁文件应该先提示用户关闭，而不是静默覆盖或者跳过不处理。

## 输出规范

按案件建一个目录，产物统一放进去：
```
<方向名>/
├── 00-索引与合并说明.md   # 候选点→最终专利的合并逻辑表、风险等级汇总表、后续建议
├── 专利①-<名称>.md / .docx
├── 专利②-<名称>.md / .docx
├── ...
└── figures/
    └── 专利①/ 专利②/ ...  # 每篇独立子目录，避免文件名冲突覆盖
```

`00-索引与合并说明.md` 是给用户/专利代理人的导航文档，必须包含：合并逻辑表（最终专利吸收了哪些候选点、为什么合并）、风险等级与优先级一览表、检索性质说明（网络初筛 vs 正式 incoPat/CNIPA 查新的区别，明确后者才是提交前必须做的）。

**这份索引是活文档，不是写完就定稿的交付物**——实际情况通常是：第一轮产出后用户会拿去审阅，隔一段时间回来要求补检索、修图、加发明人信息，每一轮新发现的问题和新做的修复都应该**追加**到索引里（带上日期区分批次），而不是覆盖重写旧的记录。这样索引本身就成了这个案件从挖掘到最终提交的完整变更历史，代理人或后续接手的人不用再问"这篇改过什么、为什么改"。

## 最后提醒

这套流程产出的是**交底书草稿**，服务对象是专利代理人二次撰写正式申请文件，不是可以直接提交的申请文件本身。任何"检索与风险提示"都基于公开网络/初步工具检索，不能替代专业检索机构的正式新颖性检索（FTO）——这句话要在每次交付时对用户说清楚，不要省略。
