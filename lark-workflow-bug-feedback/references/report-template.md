# Bug 判定标准 + 日报模板

## 一、怎么判断一条消息是不是 bug / 该不该入表

目标是从"很杂的群聊"里挑出真正的产品反馈。靠理解语义，不要只匹配关键词。

**算 bug（入表，类型=Bug）** —— 出现"产品没按预期工作"的信号：
- 报错、崩溃、闪退、卡死、无响应、黑屏
- 结果错误、数据丢失、与预期不符、精度异常
- 操作做不下去、功能失效

**算产品意见但不是 bug（按需入表）**：
- `类型=建议`：希望增加/改进某功能（feature request）
- `类型=疑问`：使用方法提问。一般**不入表**，除非问题反复出现、暗示文档或交互有缺陷——这类可作为"建议"记录。

**不入表（日报可一笔带过或忽略）**：
- 闲聊、寒暄、表情、接龙
- 内部沟通、排期讨论、与产品体验无关的话题
- 已在对话中被确认为用户误用且无产品问题

**拿不准时**：倾向于纳入并在描述里标注"待确认"。漏掉一个真 bug 的代价，比多记一条让人工删除要大。

**用回复关系串联确认与 +1**：消息的 `reply_to` 和 `@提及` 是判断"同一个 bug"的强信号。回复里出现"bug +1""我也遇到""+1"等，应合并到被回复的那条 bug：`反馈次数 +1`、追加该反馈人，不要新建行。排查类对话（"有日志吗""我私聊你""@xx 看一下"）不入表，但可作为补充描述线索。

**抽取字段时**：标题一句话讲清"什么场景下什么坏了"；描述尽量带上复现线索和发言原话要点；模块、严重程度据描述合理推断，信息不足就填"其他/一般"。

## 二、日报小节模板

每次运行生成"当天小节"，插入日报文档**顶部**（最新在上）。无新增内容时写一行"今日无新增 bug 反馈"。

```markdown
## {YYYY-MM-DD} Bug 反馈日报

> 处理区间：{起} ~ {止}　|　新增 {N} 条　合并 {M} 条　|　热点：{一句话点出被反复反馈或最严重的问题}

### 🆕 新增
1. **[{严重程度}/{模块}] {Bug标题}** —— {问题描述要点}（反馈人：{姓名}）
2. ...

### 🔁 重复 / 追加反馈
- **{Bug标题}**（累计 {反馈次数} 次，本次新增反馈人：{姓名}）
- ...

### 💡 建议 / 疑问
- {类型}：{标题} —— {要点}（{反馈人}）
- ...

—— 详见 [Bug 反馈表]({Base 链接})
```

## 三、写法约定

- 标题语气客观，不夸张、不臆断原因。
- "热点"一句话要有信息量：指出今天最该关注的那个问题，而不是套话。
- 严重程度/模块用与表格一致的取值，方便对照。
- **私信摘要**可比日报更精简：列出当天新增 bug 标题 + 一句热点 + 日报文档链接 + Base 链接即可，方便你在手机上一眼扫过。
